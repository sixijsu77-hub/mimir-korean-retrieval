# exp07 — checking a claim hard enough that it died

Measured 2026-08-12. Raw records: [`results/mteb_kor_ab.jsonl`](../results/mteb_kor_ab.jsonl),
[`results/mteb_kor_eras.jsonl`](../results/mteb_kor_eras.jsonl),
[`results/mteb_kor_era_match.jsonl`](../results/mteb_kor_era_match.jsonl). Regenerated by
`scripts/mteb_kor_ab.py` and `scripts/mteb_kor_eras.py`, both of which need `mteb` installed
— see *Reproducing*.

This page is not a pre-registered experiment. It is a verification pass on a claim that had
not been published yet, and the claim did not survive it. What survived is a stronger
version of the upstream report this repository already filed.

## The claim that was going to be made

MTEB's PR #4870, merged 2026-07-31, added one line:

```python
"kor": (None, None, "char"),  # Korean (could add a morphological analyzer later)
```

Its commit message gives the reason: *"matching the existing jpn/zho handling for no-space
scripts"*. Korean is written with spaces between 어절, unlike the Japanese, Thai, Khmer,
Burmese, Tibetan and Lao entries it was grouped with. On the three Korean datasets this
repository had loaders for, the change costs nDCG@10 on all three.

That looked like a defect worth reporting. Five checks were run before writing it up.

## Check 1 — every metric, not the one that agreed

The harness computed nDCG and recall only. MAP, MRR, hit-rate and precision were added and
validated against MTEB's own published values for `AutoRAGRetrieval`:

| Metric | MTEB published | this harness |
|---|---|---|
| ndcg_at_10 | 0.65022 | 0.65022 |
| map_at_10 | 0.59527 | 0.59527 |
| map_at_100 | 0.60302 | 0.60302 |
| mrr_at_10 | 0.595269 | 0.595270 |
| recall_at_10 | 0.82456 | 0.82456 |
| recall_at_100 | 0.99123 | 0.99123 |
| hit_rate_at_10 | 0.82456 | 0.82456 |
| precision_at_10 | 0.08246 | 0.08246 |

Eight of eight, to the precision published. The first thing the wider metric set showed was
that **Recall@100 moves the other way**: on the same three datasets it improves by +0.018,
+0.072 and +0.116. A change that costs top-10 precision and buys deep recall is a trade, not
a regression — and the ticket as drafted would have been answered in one line.

## Check 2 — every Korean task, not the three with loaders

`mteb/baseline-bm25s` publishes 27 Korean results across 24 tasks; this harness had loaders
for three of them. Running the A/B inside `mteb` itself covered **26 comparable
task/split/subset combinations**:

| | character (current) beats word | word beats character | identical |
|---|---|---|---|
| nDCG@10 | 11 | 13 | 2 |
| Recall@100 | 17 | 6 | 3 |

Median change: **−0.01471 nDCG@10, +0.04357 Recall@100**. The extremes go both ways —
`MultiLongDocRetrieval` loses 0.519, `MultilingualNanoQuoraRetrieval` gains 0.142.

**The three datasets this repository happened to have loaders for were three of the losses.**
Across everything published, the change is a coin flip on nDCG@10 and a clear gain on deep
recall. **The claim is withdrawn.** It was never posted; this page is where it is recorded
instead.

## Check 4 — run it in their library, not ours

Every number in this repository until now came from its own harness. Matching published
values is strong evidence, but "your reimplementation differs somewhere" stays available as
an answer. `mteb` 2.18.16 was installed in a separate virtualenv — the repository's own
`.venv` still has no `mteb` in it — and the baseline was run through it directly:

| | MTEB published | this harness | mteb 2.18.16 |
|---|---|---|---|
| ndcg_at_10 | 0.65022 | 0.65022 | 0.65022 |
| map_at_10 | 0.59527 | 0.59527 | 0.59527 |
| recall_at_100 | 0.99123 | 0.99123 | 0.99123 |
| mrr_at_10 | 0.595269 | 0.595270 | 0.5952694 |

Three independent paths agree. The A/B above was then done the same way — by removing the
`kor` key from `_ISO3_TO_LANG` at runtime, which reproduces the pre-#4870 state exactly and
touches nothing else.

## Check 5 — read why the change was made

The commit message, quoted above, states the premise: Korean was added as a no-space script.
That premise is wrong about Korean orthography. **It is also not what decides the question**,
because check 2 showed the effect is a wash. A correct objection to a wrong premise is still
not a defect report when the outcome does not favour either side.

## What survived: no result stamped `2.12.30` behaves like 2.12.30

The same machinery answers a sharper question. MTEB's Korean handling has had exactly three
states, all three of which can be reproduced inside `mteb` 2.18.16:

| Era | Korean handling |
|---|---|
| ≤ 2.14.1 | `stopwords="en"` and `stemmer_language="english"` hardcoded for every language, word split |
| 2.14.2 – 2.18.11 | word split, no stopwords, frequency stopwords at 0.9 |
| ≥ 2.18.12 | character unigram, frequency stopwords at 0.9 |

Every published Korean result that can distinguish them matches **exactly one**, to five
decimals:

| Task | Published | ≤ 2.14.1 | 2.14.2–2.18.11 | ≥ 2.18.12 | Behaves as | Records | Dated |
|---|---|---|---|---|---|---|---|
| BelebeleRetrieval ko-ko | 0.60865 | **0.60865** | 0.60936 | 0.66595 | ≤ 2.14.1 | 2.10.8 | 2026-03-09 |
| Ko-StrategyQA | 0.37808 | **0.37808** | 0.37814 | 0.30136 | ≤ 2.14.1 | 2.10.8 | 2026-03-30 |
| MIRACLRetrievalHardNegatives | 0.28846 | **0.28846** | 0.28907 | 0.26444 | ≤ 2.14.1 | 1.38.49 | — |
| MrTidyRetrieval | 0.19162 | 0.19166 | **0.19162** | 0.18263 | 2.14.2–2.18.11 | **2.12.30** | 2026-07-30 |
| AutoRAGRetrieval | 0.65022 | 0.79557 | 0.79557 | **0.65022** | ≥ 2.18.12 | **2.12.30** | 2026-07-01 |
| LawIRKo | 0.31795 | 0.24843 | 0.24843 | **0.31795** | ≥ 2.18.12 | **2.12.30** | 2026-07-01 |
| SQuADKorV1Retrieval | 0.83870 | 0.83685 | 0.83699 | **0.83870** | ≥ 2.18.12 | **2.12.30** | 2026-07-01 |

Three of the seven agree with the version they record. The four that do not are **exactly
the four that record `mteb_version: 2.12.30`**, and they disagree in two different
directions. 2.12.30 belongs to the ≤ 2.14.1 era; none of the four behaves that way.

Three of them — `AutoRAGRetrieval`, `LawIRKo`, `SQuADKorV1Retrieval` — were written within
90 seconds of each other on 2026-07-01 and reproduce only under code first released on
2026-08-02. That is a month after the file's own date field, not one release behind.

This is the report already open as
[embeddings-benchmark/mteb#5157](https://github.com/embeddings-benchmark/mteb/issues/5157),
which was filed on one task. It is four, and it now rests on their library rather than this
one.

## What this cost and what it bought

The claim that started this page was wrong, and finding that out took an afternoon: a wider
metric set, twenty-three more tasks, and an install of the library being criticised. Every
one of those three checks would have been skipped by anyone confident in the result — and
the first two are what killed it.

The same work is why the surviving claim is hard to answer. It is measured in the
maintainers' own code, on every published Korean result, at exact precision, with the
alternative explanations enumerated and each one matched to a specific task.

## Reproducing

```bash
# separate environment; the repository's own .venv deliberately has no mteb in it
python3 -m venv mtebenv && mtebenv/bin/pip install "mteb[bm25s]==2.18.16"

# A/B the `kor` mapping across every Korean task with a published baseline
mtebenv/bin/python scripts/mteb_kor_ab.py "AutoRAGRetrieval,LawIRKo,..." ab.jsonl

# the three code eras on the tasks that distinguish them
mtebenv/bin/python scripts/mteb_kor_eras.py "AutoRAGRetrieval,LawIRKo,..." eras.jsonl
```

Both scripts patch `mteb.models.model_implementations.bm25._ISO3_TO_LANG` in memory and pass
`stopwords` / `stemmer_language` explicitly. Nothing else is changed: the task loader, the
scoring engine and the metrics are `mteb`'s throughout. The full run is 52 + 27 records and
took about 40 minutes, most of it `MIRACLRetrieval` and `MrTidyRetrieval`.
